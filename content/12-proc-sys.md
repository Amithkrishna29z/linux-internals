## The Big Picture

"Everything is a file" has been the refrain of this whole course, and `/proc` and `/sys` are its most audacious expression. These are **virtual filesystems** — directory trees full of files that don't exist on any disk. When you `cat /proc/meminfo`, no file is read from storage; the kernel *generates the contents on the fly*, in response to your `read`, out of its own live internal state. `/proc` is a window cut directly into the running kernel, dressed up as files and directories so that every tool you already know — `cat`, `grep`, `ls`, `less`, and your own `open`/`read` code — works on kernel and process internals with zero new API. Want to know a process's memory layout, open file descriptors, command line, or scheduling state? It's all there as text under `/proc/[pid]/`. Want system-wide facts — total memory, every CPU's details, the load average, mounted filesystems? `/proc/meminfo`, `/proc/cpuinfo`, `/proc/loadavg`, `/proc/mounts`. This is how `ps`, `top`, `free`, `lsof`, and `htop` are built: they're just parsers of `/proc`.

The per-process tree is the star. For every running process there's a directory `/proc/[pid]/` (and `/proc/self/` is a magic symlink to *your own* process's directory). Inside: `status` (human-readable state — memory, UIDs, thread count, the PPID from Module 5), `cmdline` (the exact argv), `maps` (the virtual-memory segments — the *live* version of Module 7's text/data/heap/stack diagram, with real addresses and the libraries mapped in), `fd/` (a directory of symlinks, one per open file descriptor — you can literally `ls` a process's open files, which is what `lsof` does), and `stat`/`statm` (machine-readable stats). Reading `/proc/self/maps` and seeing the exact segment layout you learned about abstractly in Module 7 — now with your program's real addresses — is one of those moments where the whole mental model snaps into concrete focus. We'll write a program that reads its own `/proc/self/status` and `/proc/self/maps`, and a miniature `ps` that walks `/proc`, reads each process's info, and prints a table — and you'll realize `ps` was never magic.

Then the twist that makes `/proc` and especially **`/sys`** more than a read-only dashboard: many of these files are **writable**, and writing to them *changes kernel behavior*. `echo 1 > /proc/sys/net/ipv4/ip_forward` turns your machine into a router. `echo 3 > /proc/sys/vm/drop_caches` drops the page cache. `/sys` (sysfs) exposes the kernel's device model — every device, driver, and bus as a directory tree — with attribute files you read to query and write to control: LED brightness, CPU frequency governor, block-device schedulers. This is the structured successor to `ioctl` that Module 11 promised: instead of an opaque `ioctl(fd, MAGIC, &struct)`, you `echo` a value into a clearly-named file, discoverable with `ls` and scriptable with the shell. The `sysctl` command and `/etc/sysctl.conf` are just conveniences over writing `/proc/sys/` files. Understanding that kernel tunables *are files* demystifies system administration entirely: tuning Linux is, quite literally, reading and writing the right files.

This is a shorter, consolidating module. There's little new *syscall* material — you already know `open`/`read`/`write` — and that's the point: `/proc` and `/sys` are the payoff of the file abstraction, letting you introspect and control the kernel with the tools and code you've had since Module 3. It also sets up the finale: Module 13 goes *below* this surface into how syscalls actually reach kernel code, and Modules 14–15 into drivers and eBPF. `/proc` is the last stop where everything is still comfortably a file.

## Concepts

### 1. `/proc` as a virtual filesystem: files generated by the kernel

**What it is:** `/proc` (procfs) is a **virtual filesystem**: it looks like a normal directory tree, but its files have **no backing storage** — the kernel synthesizes their contents at the moment you `read` them, from its live internal data structures. `cat /proc/uptime` doesn't read a file; it calls into kernel code that formats the current uptime as text and hands it to your `read`.

```
   $ cat /proc/uptime
   34521.87 285043.12          ← generated NOW, from kernel state (not stored anywhere)

   ordinary file:   read() → disk blocks → your buffer
   /proc file:      read() → KERNEL CODE runs → formats live state → your buffer
                    (ls -l shows size 0: there's nothing on disk to measure)
```

**Why it exists:** The kernel holds a wealth of state — process tables, memory stats, device info — that programs need to inspect. Rather than invent dozens of specialized syscalls (a `getmeminfo()`, a `getprocesslist()`, ...), Linux exposes it all through the *filesystem* interface you already have. This makes kernel state universally accessible: any language that can open a file can read it, any shell tool works on it, no bindings needed. It's the "everything is a file" philosophy turned into a kernel-introspection API — maximal reuse of one abstraction.

**Java analogy:** Java gives you slivers of this through typed APIs — `Runtime.availableProcessors()` (a parse of `/proc/cpuinfo` or a syscall), `OperatingSystemMXBean.getSystemLoadAverage()` (`/proc/loadavg`), `ProcessHandle` (`/proc/[pid]/`). Each is a JVM method wrapping a read of these virtual files. There's no Java concept of "the filesystem *is* the kernel API," because Java abstracts the OS away — which is exactly why dropping to `/proc` reveals what those tidy MXBean methods are really doing.

### 2. The per-process tree: `/proc/[pid]/` and `/proc/self/`

**What it is:** For every process (PID *N*) there's a directory `/proc/N/` exposing that process's state; `/proc/self/` is a special symlink that always points to *the reading process's own* directory. Key entries:

```
   /proc/[pid]/
     ├── status    ← human-readable: Name, State, PPid, VmRSS, Threads, Uid, ...
     ├── cmdline   ← the argv, NUL-separated (the exact command line)
     ├── maps      ← virtual memory segments: address range, perms, mapped file
     ├── fd/       ← a directory of symlinks: one per OPEN file descriptor
     │    ├── 0 -> /dev/pts/2   (stdin)
     │    ├── 1 -> /dev/pts/2   (stdout)
     │    └── 3 -> /home/me/data.txt
     ├── stat      ← machine-readable stats (one line, many fields)
     ├── cwd       ← symlink to the process's working directory
     └── exe       ← symlink to the executable
```

**Why it exists:** Process introspection is a universal need — debuggers, monitors, `ps`, `top`, `lsof` all must inspect processes — and per-process directories make each process's state browsable and readable with ordinary file operations. `/proc/self/` exists so a process can inspect *itself* without knowing its own PID (though `getpid()` works too). `fd/` being a directory of symlinks means "what files does this process have open?" is answered by `ls` — which is precisely what `lsof` does.

**Java analogy:** `ProcessHandle.of(pid)` and `ProcessHandle.current()` mirror `/proc/[pid]/` and `/proc/self/`; `.info().commandLine()` reads `cmdline`, `.info().command()` the `exe` link, `.pid()`/`.parent()` map to `status`'s PPid. The JVM implements these by reading these exact files on Linux. `ManagementFactory.getRuntimeMXBean()` similarly surfaces bits of `/proc/self/`.

### 3. System-wide files: `meminfo`, `cpuinfo`, `loadavg`, and friends

**What it is:** Alongside the per-process directories, `/proc` has system-global files describing the whole machine:

```
   /proc/meminfo    ← MemTotal, MemFree, Buffers, Cached, SwapTotal, ...  (what `free` parses)
   /proc/cpuinfo    ← per-core: model name, MHz, flags, cache size        (what `lscpu` parses)
   /proc/loadavg    ← 1/5/15-min load averages + running/total procs      (what `uptime` shows)
   /proc/mounts     ← every mounted filesystem                            (like `mount` output)
   /proc/stat       ← cumulative CPU ticks (user/system/idle), used to compute CPU %
   /proc/[pid]/...  ← and the per-process tree from Concept 2
```

**Why it exists:** These are the canonical sources of truth for system state, and the tools you use daily are thin parsers over them: `free` reads `/proc/meminfo`, `uptime` reads `/proc/loadavg`, `top`'s CPU percentages come from sampling `/proc/stat` twice and differencing. Exposing this as text files means the monitoring ecosystem (from `htop` to Prometheus node_exporter) needs no special kernel API — just file reads. It's a stable, documented, language-agnostic contract for "the state of this machine."

**Java analogy:** `OperatingSystemMXBean` (`getTotalMemorySize`, `getFreeMemorySize`, `getSystemLoadAverage`, `getCpuLoad`) is the JVM reading and parsing these files for you. When a Java monitoring agent reports host memory or CPU, it's ultimately sampling `/proc/meminfo` and `/proc/stat`. Knowing the underlying files tells you what those metrics *actually* mean (e.g. why "free" memory looks alarmingly low — because `Cached` is reclaimable, a nuance the raw file makes visible).

### 4. `/sys` (sysfs): the device model as a filesystem

**What it is:** `/sys` (sysfs) is a second virtual filesystem, newer and more structured than `/proc`, exposing the kernel's **device model** — every device, driver, bus, and kernel subsystem — as a directory tree of **attribute files**. Each attribute is typically a tiny file you `read` to query and (if writable) `write` to control:

```
   /sys/class/net/eth0/address        ← the MAC address (read)
   /sys/class/net/eth0/mtu            ← the MTU (read/write)
   /sys/block/sda/queue/scheduler     ← the I/O scheduler (read shows choices, write selects)
   /sys/devices/.../cpufreq/scaling_governor  ← CPU frequency governor (read/write)
   /sys/class/leds/.../brightness     ← an LED's brightness (write a number)
```

**Why it exists:** `/proc` grew organically into a grab-bag of unrelated things (process info, kernel tunables, hardware, random stats), which became messy. `/sys` was designed deliberately to give the **device model** a clean, hierarchical, one-value-per-file structure — the discoverable, scriptable successor to `ioctl` (Module 11) for device attributes. Its rule of thumb ("one value per file") makes it self-documenting: `ls` a directory to see a device's attributes, `cat` one to read it, `echo` to set it. It's how modern Linux exposes and tunes hardware.

**Java analogy:** No direct equivalent — device control is below the JVM — but the *design philosophy* (a discoverable tree of named, individually-addressable configuration values) is one you know from hierarchical config systems: JMX's MBean attribute tree, or a `/`-separated key-value config store (etcd, ZooKeeper). `/sys` is the kernel's MBean tree, addressed as files instead of via a management protocol.

### 5. Reading vs writing: introspection *and* control

**What it is:** `/proc` and `/sys` files split into two roles. **Reading** them is introspection (all of Concepts 1–4). **Writing** to the writable ones *changes kernel behavior* — most importantly under `/proc/sys/` (the kernel tunables, aka `sysctl`) and throughout `/sys`:

```
   echo 1 > /proc/sys/net/ipv4/ip_forward       ← enable IP forwarding (become a router)
   echo 3 > /proc/sys/vm/drop_caches             ← drop page/inode/dentry caches
   echo 1024 > /proc/sys/net/core/somaxconn      ← raise the listen() backlog limit
   echo performance > /sys/.../scaling_governor   ← pin CPU to max frequency

   sysctl -w net.ipv4.ip_forward=1               ← the SAME thing; sysctl is a wrapper
                                                    over writing /proc/sys/net/ipv4/ip_forward
```

**Why it exists:** Exposing tunables as writable files means configuring and controlling the kernel needs no special tool — the shell's `echo` and redirection, or any program's `write`, suffice. `sysctl`/`/etc/sysctl.conf` are conveniences layered on top (they translate `net.ipv4.ip_forward` to the file path). This is the culmination of "everything is a file": you don't just *observe* the kernel through the filesystem, you *steer* it. Persisting a tuning is just arranging for the right file to be written at boot.

**Why care / the lesson:** Every "tune this Linux setting" instruction you'll ever follow — raising connection limits, enabling forwarding, adjusting swappiness, changing an I/O scheduler — reduces to writing a `/proc/sys` or `/sys` file. Recognizing that dissolves the mystery of kernel configuration: there's no hidden registry or opaque API, just files. It also demands respect: these writes take effect *immediately* and system-wide, so a wrong value can degrade or hang the machine.

**Java analogy:** The closest analogue is a writable JMX attribute or a runtime `System.setProperty` that actually changes behavior — but those live inside your JVM, whereas `/proc/sys` writes reconfigure the *whole kernel*. The reach is the difference: Java control surfaces are process-scoped; these files are machine-scoped. That scope is why they usually require root.

## Code

### Program 1 — `procpeek.c`: read your own status and memory map

```c
/* procpeek.c
 *
 * Reads the process's OWN /proc entries: /proc/self/status (selected human-
 * readable fields) and /proc/self/maps (the live virtual-memory segments --
 * the concrete version of Module 7's text/data/heap/stack diagram). No special
 * API: /proc files are opened and read like any other file.
 *
 * Compile:  gcc -Wall -Wextra -o procpeek procpeek.c
 * Run:      ./procpeek
 */

#include <stdio.h>
#include <stdlib.h>
#include <string.h>

/* Print lines from /proc/self/status whose key is one we care about. */
static void show_status(void)
{
    FILE *f = fopen("/proc/self/status", "r");
    if (!f) { perror("open status"); return; }

    char line[256];
    const char *want[] = { "Name:", "Pid:", "PPid:", "VmRSS:", "VmSize:",
                           "Threads:", "State:", NULL };
    printf("== /proc/self/status ==\n");
    while (fgets(line, sizeof line, f)) {
        for (int i = 0; want[i]; i++)
            if (strncmp(line, want[i], strlen(want[i])) == 0)
                fputs(line, stdout);
    }
    fclose(f);
}

/* Print the memory map: each line is  addr-range perms offset dev inode  path */
static void show_maps(void)
{
    FILE *f = fopen("/proc/self/maps", "r");
    if (!f) { perror("open maps"); return; }

    printf("\n== /proc/self/maps (virtual memory segments) ==\n");
    char line[512];
    while (fgets(line, sizeof line, f)) {
        /* Highlight the interesting named regions: heap, stack, our binary. */
        if (strstr(line, "[heap]") || strstr(line, "[stack]") ||
            strstr(line, "procpeek") || strstr(line, "[vdso]"))
            fputs(line, stdout);
    }
    fclose(f);
}

int main(void)
{
    /* Allocate something so [heap] is populated and visible in maps. */
    char *p = malloc(1 << 20);   /* 1 MB */
    if (p) p[0] = 'x';            /* touch it so a page is backed (Module 7) */

    show_status();
    show_maps();

    free(p);
    return 0;
}
```

**Expected output:**
```
$ ./procpeek
== /proc/self/status ==
Name:   procpeek
State:  R (running)
Pid:    18422
PPid:   18001
VmSize: 6284 kB
VmRSS:  1408 kB
Threads:        1

== /proc/self/maps (virtual memory segments) ==
561f2a1c8000-561f2a1c9000 r-xp 00000000 08:01 1837 /home/me/procpeek   ← text (r-x)
561f2a3c9000-561f2a3ca000 r--p ...                 /home/me/procpeek   ← rodata
561f2b4d0000-561f2b4f1000 rw-p 00000000 00:00 0    [heap]              ← heap (rw-)
7ffe1c2a0000-7ffe1c2c1000 rw-p 00000000 00:00 0    [stack]             ← stack (rw-)
7ffe1c3d4000-7ffe1c3d6000 r-xp 00000000 00:00 0    [vdso]              ← kernel-provided
```

**Walkthrough of the non-obvious parts:**
- **`/proc/self/` needs no PID** — the kernel resolves `self` to whatever process is doing the reading, so a program inspects itself without calling `getpid()`. `fopen("/proc/self/status", "r")` is an ordinary `fopen`; these are just files.
- **`maps` is Module 7 made concrete.** Each line is `address-range perms offset device inode pathname`. The `perms` column is the payoff: `r-xp` = the **text** segment (readable, executable, not writable — your code), `rw-p` = the **heap** and **stack** (readable/writable, not executable — data). You're seeing the exact segment model from Module 7 with *real* addresses from *this* run, and the `r-x` vs `rw-` split is the memory-protection that stops code from being modified and data from being executed (W^X).
- **`[heap]` only shows meaningfully after you allocate** — we `malloc(1MB)` and touch it so the heap segment exists and is sized; without any allocation the heap may be tiny or absent. The touch (`p[0]='x'`) forces a page to be backed (demand paging, Module 7), which is also why `VmRSS` (resident) is smaller than `VmSize` (virtual).
- **`[vdso]`** is a small region the *kernel* maps into every process — a shared library of fast syscall implementations (like `gettimeofday`) that run without a full kernel transition. Seeing it here previews Module 13's syscall mechanics.
- `VmRSS` vs `VmSize` in `status` are exactly the resident-vs-virtual distinction from Module 7's demand-paging: virtual address space reserved vs physical RAM actually backing it.

### Program 2 (Project) — `myps.c`: a tiny `ps` by walking `/proc`

```c
/* myps.c
 *
 * A miniature `ps`: walk /proc, and for every entry that is a PID directory,
 * read /proc/[pid]/status to extract the name, state, PPID, and resident
 * memory, then print a table. This is essentially how ps/top/htop work --
 * they parse /proc. No special API, just readdir + fopen + fgets.
 *
 * Compile:  gcc -Wall -Wextra -o myps myps.c
 * Run:      ./myps
 */

#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <ctype.h>
#include <dirent.h>

/* Pull one "Key:\tvalue" field out of a status file into `out`. */
static int field(const char *path, const char *key, char *out, size_t outsz)
{
    FILE *f = fopen(path, "r");
    if (!f) return -1;
    char line[256];
    int found = -1;
    size_t klen = strlen(key);
    while (fgets(line, sizeof line, f)) {
        if (strncmp(line, key, klen) == 0) {
            /* skip the key and any leading whitespace */
            char *v = line + klen;
            while (*v == ':' || *v == ' ' || *v == '\t') v++;
            v[strcspn(v, "\n")] = '\0';
            snprintf(out, outsz, "%s", v);
            found = 0;
            break;
        }
    }
    fclose(f);
    return found;
}

int main(void)
{
    DIR *d = opendir("/proc");
    if (!d) { perror("opendir /proc"); return 1; }

    printf("%7s  %-20s  %-5s  %10s  %s\n", "PID", "NAME", "STATE", "RSS(kB)", "PPID");

    struct dirent *e;
    while ((e = readdir(d)) != NULL) {
        /* A process directory is named entirely of digits. */
        if (!isdigit((unsigned char)e->d_name[0])) continue;

        char path[300];
        snprintf(path, sizeof path, "/proc/%s/status", e->d_name);

        char name[64] = "?", state[16] = "?", rss[16] = "0", ppid[16] = "?";
        if (field(path, "Name", name, sizeof name) < 0)
            continue;                       /* process vanished between readdir and open */
        field(path, "State", state, sizeof state);
        field(path, "VmRSS", rss, sizeof rss);   /* kernel threads have no VmRSS */
        field(path, "PPid",  ppid, sizeof ppid);

        /* State is like "R (running)"; keep just the letter. */
        char st = state[0];
        printf("%7s  %-20s  %-5c  %10s  %s\n", e->d_name, name, st, rss, ppid);
    }

    closedir(d);
    return 0;
}
```

**Expected output (abridged):**
```
$ ./myps
    PID  NAME                  STATE      RSS(kB)  PPID
      1  systemd               S            11840  0
    843  sshd                  S             7020  1
   1002  bash                  S             5460  843
  18500  myps                  R             1360  1002
  ...
```

**Walkthrough of the non-obvious parts:**
- **`ps` is not magic** — it's this: `opendir("/proc")`, keep the entries whose names are all digits (those are PIDs), and for each read `/proc/[pid]/status`. `top` and `htop` add sampling over time (re-reading periodically) and more fields, but the core is exactly this loop. Once you've written it, `ps`/`top`/`lsof` are forever demystified.
- **The all-digits test** distinguishes PID directories (`/proc/1`, `/proc/843`) from the many non-PID entries in `/proc` (`/proc/meminfo`, `/proc/cpuinfo`, `/proc/self`, ...). Simple and robust: kernel names process dirs numerically.
- **Processes can vanish mid-scan** — between `readdir` seeing `/proc/18499` and our `fopen` of its `status`, that process may exit, so `fopen` fails. We treat that as "skip" rather than an error (the `field(...) < 0 → continue`). This time-of-check/time-of-use reality is inherent to introspecting a *live* system, and real `ps` handles it the same way.
- **Kernel threads have no `VmRSS`** (they share the kernel's address space, not a user one), so `field(..., "VmRSS", ...)` fails for them and we keep the default `"0"`. That's why some entries show 0 RSS — they're kernel worker threads (`[kworker/...]`), not user processes.
- **`State`** is a single letter with a description (`R (running)`, `S (sleeping)`, `Z (zombie)` — the Module 5 zombie, visible here!, `D (uninterruptible)`); we keep just the letter. Seeing a `Z` in your own `myps` output is Module 5's theory made observable.

## Under the Hood

Run `strace -e trace=openat,read ./procpeek` and `cat /proc/uptime` under strace to see that these "files" are just `open`+`read` — the magic is entirely on the kernel's side:

```
# procpeek reading its own status -- ordinary file syscalls:
openat(AT_FDCWD, "/proc/self/status", O_RDONLY)  = 3            ← [1] just an open()
read(3, "Name:\tprocpeek\nUmask:\t0022\nState:\tR (running)\n"..., 4096) = 1203  ← [2]
read(3, "", 4096)                                = 0            ←     EOF
close(3)
openat(AT_FDCWD, "/proc/self/maps", O_RDONLY)    = 3
read(3, "561f2a1c8000-561f2a1c9000 r-xp 00000000 08:01 ...", 4096) = 2891       ← [3]

# the size on disk is ZERO -- there's nothing stored:
$ ls -l /proc/self/status
-r--r--r-- 1 me me 0 Jul 29 03:00 /proc/self/status               ← [4] size 0, yet has content
```

Annotated:
1. **`openat(..., "/proc/self/status", O_RDONLY) = 3`** — opening a `/proc` file is an *ordinary* `open`, returning an ordinary fd (3). Your program can't tell (and needn't care) that it's virtual; it's the same fd interface as a disk file.
2. **`read(3, "Name:\tprocpeek\n...", 4096) = 1203`** — here's the sleight of hand: the bytes returned did **not** come from disk. The `read` syscall entered the kernel, which ran the procfs handler for `status`, which walked the *live* task struct for this process and *formatted the text on the spot*, then copied it to your buffer. The content is manufactured per-read.
3. **`/proc/self/maps`** — same: the kernel walked this process's VMA (virtual memory area) list and formatted each segment as a line. Read it a second later after a big `malloc` and the `[heap]` line grows — because it reflects *current* state each time.
4. **`ls -l` shows size 0`** — the killer detail. A normal file's size is stored metadata; a `/proc` file has *no stored content*, so its size is reported as 0 even though `read` yields plenty. "Size 0 but non-empty when read" is the unmistakable signature of a kernel-generated virtual file.

The headline: **`/proc` and `/sys` files are opened and read with the exact same `openat`/`read`/`close` as any file — the entire difference is that the kernel *computes* their contents from live state at read time instead of fetching stored bytes.** That's why every tool that works on files works on kernel state, and why `ps` is a `readdir` loop. The file interface reaches all the way into the kernel's live internals.

## Try This

Ordered easy → hard.

1. **(Easy) Confirm `/proc` files are generated live.** `cat /proc/uptime` twice a few seconds apart — the numbers change. `cat /proc/meminfo | head`, then start a big program and `cat` again — `MemFree` drops. `ls -l /proc/self/status` shows size 0. *Hint: content that changes per read and reports size 0 can't be a stored file — the kernel makes it on demand.*

2. **(Easy) List a process's open files by hand.** Pick a PID (e.g. your shell, `echo $$`), then `ls -l /proc/[pid]/fd/` — you'll see the symlinks for stdin/stdout/stderr and every open file/socket. Compare to `lsof -p [pid]`. *Hint: `lsof` is essentially this `ls` plus name resolution — you just did its core job.*

3. **(Medium) Extend `myps` into a mini-`top`.** Add reading `/proc/[pid]/stat` fields 14–15 (utime/stime), sample twice a second apart, and compute per-process CPU% from the delta. Sort by CPU descending. *Hint: CPU% is (Δticks / Δtime) — `top` samples `/proc/[pid]/stat` (and `/proc/stat`) exactly this way; there's no other source.*

4. **(Medium) Read your process's live memory map growing.** In `procpeek`, print `/proc/self/maps` before and after a large `malloc`+touch, and diff the `[heap]` line's address range. Then `mmap` a file and see a *new* region appear named after the file. *Hint: `maps` is recomputed each read, so it reflects allocations you just made — the segment model is dynamic and observable.*

5. **(Hard) Safely tune a kernel parameter and revert it.** Read `/proc/sys/net/core/somaxconn` (the max `listen` backlog), note the value, `echo` a larger one (as root), confirm with `sysctl net.core.somaxconn`, then restore the original. Explain how this relates to Module 9's `listen(fd, backlog)`. *Hint: `somaxconn` caps the backlog your `listen()` can request — writing the file reconfigures the live kernel; `sysctl` is just a wrapper over this write.*

## Gotchas

- **`/proc` files have size 0 but aren't empty.** `ls -l` reports 0 bytes because there's nothing stored; you must `read` to get content. Tools that stat-then-allocate-exact-size (or trust the size) mis-handle `/proc` — always read until EOF rather than trusting the reported length.

- **Race conditions reading a live system.** A process can exit between `readdir("/proc")` seeing its directory and your `open` of its `status` — expect and tolerate `ENOENT`/open failures (skip, don't crash). Likewise a file's contents can change between two reads. Introspecting a running system is inherently a moving target; write defensively.

- **`/proc/[pid]/cmdline` is NUL-separated, not space-separated.** The arguments are separated by `\0` bytes (so the original argv is faithfully reconstructable), and the whole thing may or may not end in a `\0`. Printing it naively shows the args run together; replace `\0` with spaces to display it. A common first-parse surprise.

- **Writing `/proc/sys` and `/sys` takes effect immediately and system-wide.** These aren't sandboxed settings — `echo`ing a bad value into a tunable can degrade or hang the whole machine, right now, for every process. Know what a parameter does before writing it, test on non-production, and remember most writes need root. Respect the reach.

- **Not everything in `/proc` is a process or stable.** `/proc` mixes per-process dirs, system files, and kernel tunables, and some entries are kernel-version-specific or require privileges to read (`/proc/[pid]/` of other users' processes may be restricted by `hidepid`). Don't assume a file exists or is readable across kernels/distros; check and degrade gracefully.

- **`/proc` field formats can shift across kernel versions.** `/proc/[pid]/stat`'s field positions, `/proc/meminfo`'s keys, etc., are mostly stable but have grown over time. Parse by *key name* (in `status`/`meminfo`) rather than fixed byte offsets where possible, and don't hard-code field counts that a newer kernel might extend.

- **Prefer `/sys` over `/proc` for device attributes (and don't overuse `/proc` for new things).** `/proc` accreted a lot of non-process cruft historically; the modern convention is process/kernel info in `/proc`, device model in `/sys`. When both exist for something hardware-related, `/sys`'s one-value-per-file structure is the cleaner, more stable choice.

<details>
<summary><b>Checkpoint Answers</b></summary>

1. `/proc` is **virtual** because its files have no backing storage — the kernel **synthesizes their contents at read time** from its live internal data structures. When you `read /proc/meminfo`, the `read` syscall enters the kernel, which runs the procfs handler that formats the current memory statistics as text and copies them into your buffer; nothing is fetched from disk. The visible clue is that `ls -l` reports **size 0** for these files (there's no stored content to measure), even though reading them returns plenty of data — "size 0 but non-empty when read" is the signature of a kernel-generated file.

2. For each process PID *N* there's a directory `/proc/N/`: **`status`** gives human-readable state (name, State, PPid, VmRSS/VmSize, Threads, UIDs); **`cmdline`** is the exact argv (NUL-separated); **`maps`** lists the virtual-memory segments (address range, permissions, mapped file) — the live Module 7 layout; **`fd/`** is a directory of symlinks, one per open file descriptor, pointing at the files/sockets/devices the process has open. `/proc/self/` is a magic symlink resolving to the **reading process's own** directory (so a process inspects itself without knowing its PID). `lsof` works by reading `/proc/[pid]/fd/` (and resolving the symlink targets) — listing open files *is* listing that directory.

3. Algorithm: `opendir("/proc")`, iterate entries, keep those whose names are **all digits** (those are PID directories), and for each read `/proc/[pid]/status` (or `stat`) to extract name/state/PPID/RSS, then print a row. (`top`/`htop` additionally re-sample over time.) Two live-system complications: (a) a process can **exit between `readdir` and `open`**, so the `status` open fails with `ENOENT` — you must skip it, not crash; (b) **kernel threads have no `VmRSS`** (no user address space), so that field is absent and must be defaulted. More generally, contents can change between reads — introspection is a moving target.

4. `/proc/[pid]/maps` is the **concrete, live version of Module 7's address-space diagram**: each line is a virtual-memory segment with its real address range for this run. The **permissions column** shows the segment's protection: `r-xp` marks the **text** segment (readable, executable, not writable — code, so it can't be modified), while `rw-p` marks **heap** and **stack** (readable/writable, not executable — data), the W^X protection. **`VmRSS` (resident) is smaller than `VmSize` (virtual)** because of demand paging: `VmSize` is all the virtual address space reserved, but only the pages actually *touched* are backed by physical RAM (counted in `VmRSS`) — reserved-but-untouched memory costs no RAM.

5. Many `/proc/sys` and `/sys` files are **writable**, and writing them changes kernel behavior immediately and system-wide. Example: `echo 1 > /proc/sys/net/ipv4/ip_forward` enables IP forwarding (turns the host into a router); `echo performance > /sys/.../scaling_governor` pins CPU frequency. **`sysctl`** is just a convenience wrapper that maps dotted names (`net.ipv4.ip_forward`) to the corresponding `/proc/sys/` file path and reads/writes it — `sysctl -w net.ipv4.ip_forward=1` *is* writing that file (and `/etc/sysctl.conf` persists such writes at boot). Danger: these writes take effect instantly for the **whole machine**, so a wrong value can degrade or hang the system, and most require root — power that demands you know what a parameter does before setting it.
